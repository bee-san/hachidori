## Problem

Hachidori has one popup renderer. Restyling it after construction still pays to build Default's toolbar, cards, pitch graphs and metadata, even when a theme hides them.

**Themes must BECOME the popup. When Nazeka is selected, construct Nazeka directly: do not run Default's renderer, build its unused UI, or apply its layout CSS underneath.**

This is the current design, superseding the old `Default → onRender() → rearrange DOM` prototype. The priorities are **a usable experimental Theme Store, a faithful Nazeka theme, and avoiding unnecessary rendering work**.

## Expected behavior

### Initial MVP

- Settings → Advanced → Experimental features enables **Theme Store** in Design, using the existing experimental registry and revisioned options path.
- The Store offers **Default** (the currently existing Hachidori popup) and **Nazeka** in a **horizontal carousel of cards**. Each card shows the theme's **screenshot, name, description and benchmark result**.
- Each card has a **“Use” button** that immediately selects and applies that theme, including the live Design preview. Theme activation must not require a separate Save/Apply action or browser restart.
- Include a link to [hachidori-themes](https://github.com/bee-san/hachidori-themes).
- Selecting Nazeka resolves its renderer **before** constructing result content. It creates compact expression/reading/gloss rows and plain kanji information directly from the lookup data. Audio, Anki, keyboard actions, Back and nested lookups continue through Hachidori core.
- Nazeka should look and behave like Nazeka. It uses genuine text rendering of dictionary data; it is not the separate raw/minimal “Wicked” experiment.
- Default preserves the existing rich popup. Existing palette choices continue to use Default. Hiding the experimental Store preserves the selected theme and settings.
- Both the real popup and Design preview use the selected renderer.
- Executable theme modules are maintainer-reviewed, pinned, bundled extension code. They ship with releases and are never downloaded for execution at runtime. This is a review boundary, not a JavaScript sandbox.

### Rendering and CSS ownership

```text
Lookup → structured result model → selected theme renderer → popup DOM
                                   selected theme CSS      → appearance
```

Core owns lookup/deinflection, request identity and cancellation, navigation, audio/Anki/keyboard actions, positioning, dismissal and nested-popup lifecycle. The renderer owns its content DOM and appearance. Default and Nazeka implement the same versioned core-facing view contract; themes receive structured data, not Default DOM to scrape.

Shared helpers are optional building blocks. A renderer may request safe glossary rendering, headwords, pitch widgets or action controls; unused components must not be created. Document lifecycle behavior for incremental results, Show more, presentation changes, loading/error/empty states, Back, focus and cleanup.

Apply only:

1. Minimal shared popup infrastructure.
2. Shared component styles actually needed by that renderer.
3. Scoped dictionary-content styles, only when requested.
4. The selected renderer's CSS.
5. The user's Custom CSS, last.

Default's card/toolbar/layout rules belong to Default. **Do not apply `reader.css`'s Default layout beneath Nazeka and override it.** CSS-only palettes may deliberately reuse Default.

### Dictionary content is the renderer's choice

| Mode | Rendering work | Dictionary CSS |
| --- | --- | --- |
| **Rich** | Existing sanitised structured definitions, supported images and links | Scoped styles may be requested |
| **Text** | Flatten data directly to text; no structured dictionary DOM, images or dictionary links | None by default |
| **None** | Do not create definition DOM; keep the data available to the renderer | None by default |

Nazeka uses **text**; Default retains **rich**. Add a true data-level `glossaryToPlainText()` or equivalent. **Do not use `appendTextOnlyGlossary()` as plain-text mode:** it can construct structured DOM. Do not build rich HTML just to extract `textContent`. Dictionary content remains untrusted even though theme code is reviewed.

### Switching and failures

Retire the old view, listeners and stylesheet set when switching renderers, retaining the core model/navigation state and rejecting stale work. If a renderer throws, clean up its partial view, remove its CSS, and render the current model with Default and Default's CSS. Preserve the selected preference, warn once, and disable the failing renderer for that page. Do not leave failed-theme CSS over Default.

## Environment

- Chrome MV3 popup, Settings Design preview, Firefox package and GSM overlay integration.
- Starting boundary: `content.js` → `buildLevelUi()` / `HDPopup.createPopupView()`; related files are `render/glossary.js`, `render/reader.css`, `design-preview.js` and `reader-options.js`.
- Use the existing production hover benchmark and record the exact revisions, archives, browser and environment for new measurements.

## Benefit to the creator

Choose a familiar compact reading popup while paying only for the presentation selected. Share the existing lookup and action engine, make themes reviewable in their own repository, and measure whether less rendering work improves the actual reading experience.

## Proposed solution and delivery

1. Introduce the smallest shared renderer boundary that supports Default and direct Nazeka. Resolve the renderer before content construction, separate its CSS, and provide optional data-level text rendering and shared action bindings.
2. Add the experimental Store and matching Design preview with Default/Nazeka. Keep the initial delivery small enough to try by hand.
3. Deliver the Hachidori change through a PR and the repository's required merge gates. **Keep local validation basic and focused**, with real-popup screenshots and checks that prove the renderer boundary; do not expand this MVP into an exhaustive new test suite.
4. Maintain sources in [hachidori-themes](https://github.com/bee-san/hachidori-themes): one folder per theme, metadata, CSS, optional renderer, screenshot, attribution and benchmark evidence. Review through PRs and vendor a pinned distribution into Hachidori. The extension does not parse YAML or download executable themes.
5. Benchmark direct Nazeka against Default with repeated, identical inputs. Preserve the transformation prototype as a separately labelled historical comparison. Follow up with additional themes/catalogue tooling after the MVP works.

### Performance requirements

Direct rendering gives simpler themes an opportunity to do less work; it does not guarantee faster lookup. Measure cold-first hover, first correct frame, complete stable result, kanji open, DOM construction, script/style/layout/paint work, node counts and memory as supported by the harness. Record raw results, repeated samples, revisions and limitations.

Verify that Nazeka **does not construct Default UI, invoke rich glossary rendering, or load dictionary CSS**. Do not measure only the theme function or count hidden nodes as avoided work. The old `onRender` p95 budget measured an extra finishing pass and is not a budget for an entire replacement renderer. Investigate measured regressions and report the result honestly. Every accepted theme needs benchmark evidence.

## MVP acceptance

- [ ] Experimental Store presents Default/Nazeka in a horizontal carousel of cards, each showing screenshot, name, description and benchmark result.
- [ ] Each card's “Use” button applies the theme immediately and updates the live preview; no separate Save/Apply action or restart.
- [ ] Store links to the themes GitHub repository.
- [ ] Nazeka is the popup: no Default renderer call, unused Default DOM or Default layout stylesheet on its path.
- [ ] Genuine data-level text definitions: no rich dictionary DOM, images, links or dictionary CSS.
- [ ] Default and existing palette behavior retained; live popup and preview agree.
- [ ] Shared core actions/navigation work, with a documented view/update/cleanup contract.
- [ ] Switching and failures clean up the previous renderer and stylesheet set; fallback uses Default's own CSS.
- [ ] Focused basic checks and screenshots make the MVP ready for manual testing.
- [ ] Pinned theme sources and comparable benchmark evidence, with no assumed speedup.

Remote catalogue refresh, live CSS-only installs, migrating all palettes, additional themes and the separate Wicked experiment are follow-ups. They must not delay the Default/Nazeka MVP.
